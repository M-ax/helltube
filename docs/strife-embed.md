# Strife desktop embed

The separate `/embed/strife.html` entry point reuses Helltube's login, room navigation, player and queue. The ordinary website retains browser screen sharing. Strife probes the entry point's `helltube-embed` marker and falls back to the ordinary page on older deployments. Build with `npm run build`; both HTML entry points are included in the static deployment.

The embed admits a versioned `helltube.strife` postMessage protocol only when loaded as a frame with an exact HTTP loopback parent origin (including its port) and a session nonce in the URL fragment. Messages check the sender window, origin, protocol version, session, and a fresh connection challenge selected by the host on each load. This does not give the frame access to Strife's native capability or Mumble controls.

The host can select rooms and change local playback mute/volume. The frame reports account/room identity, connection state, available rooms and playback preferences. If the host advertises native sharing, **Share desktop** delegates to Strife's window/display picker instead of the browser capture dialog. If the helper is unavailable, Helltube keeps its existing browser-sharing controls. The native helper currently targets Windows x64 development builds of Strife; it is not a production download claim.

Sharing uses a frame-generated request ID bound to its current room and generation. The host requests credentials only for that active request; stale replies are revoked. State changes, Stop, reload and sign-out retire the request. Strife owns the publisher lifetime and shows connection/error status. Helltube playback is muted while native sharing is active to avoid recapturing it in system audio.

`POST /api/rooms/:id/strife-token` requires the existing authenticated session, room membership and a non-automated room. It returns the same `{token,path,expires}` shape as the manual OBS endpoint, but uses a separate `strife` purpose. One Strife credential per user/room can coexist with the standalone OBS credential. Both remain publishing-only, hashed in storage, and bound to the issuing login session. `DELETE` on the Strife route requires `{token}` in the JSON body and revokes only that exact credential; cleanup of a superseded request cannot stop a newer share. Legacy persisted OBS keys without a purpose remain ordinary OBS keys.

The desktop uses the existing WHIP ingest and relay. New endpoints do not create another account system, streaming listener, or transcoder. The protocol does not expose arbitrary server administration, native commands, or login cookies.

## Direct HTTP playback

An updated Helltube server paired with Strife preview.5 or newer can send queued HLS directly from the embedded browser to metal, bypassing the desktop's HTTP proxy for manifests, keys, initialization data and segments. Older Strife installers keep their existing proxy path. WebRTC sharing is unchanged.

The authenticated `/api/config` and `/api/media/:jobId/access` requests negotiate this using `X-Strife-Media-Origin`. Strife removes any incoming value and supplies its own exact canonical `http://127.0.0.1:<port>` origin. With `BARE_METAL_ORIGIN` configured, the server advertises `strifeDirectMedia: 1` and `strifeDirectMediaOrigin`. The latter preserves the real metal origin through Strife; `bareMetalOrigin` remains rewritten for existing upload/file proxy behavior. No blanket loopback CORS permission is added to ordinary APIs or direct uploads/files.

Negotiated media access returns a versioned grant signed for the media job, exact recipient origin (including port), login session and ten-minute deadline. Each request and preflight checks the grant, current session and room membership. A cookie cannot substitute for the grant. Playlists copy the original grant into keys, init data and segments rather than extending its lifetime. Only GET/HEAD and `Range`/`Content-Type` preflights are allowed.

The authenticated access response includes server `issuedAt` and `expiresAt` timestamps. The player converts their difference into a monotonic deadline, conservatively subtracting the whole request duration, so client clock skew or wall-clock changes cannot trigger renewal loops. These fields schedule renewal only; metal still authenticates the signed grant and enforces its expiry. The player starts reacquiring authenticated access 30 seconds before expiry, including while paused. It keeps the current decoder until replacement access succeeds, then aligns playback to current room time without a second access request. One renewal is allowed in flight per source; leaving or switching sources aborts it and discards late responses. Transient failures retry with 1/2/4/8-second backoff (at most five attempts, ten seconds per request, only while the old deadline permits); denial, invalid access, exhausted retries or failure after a background tab wakes past expiry stop playback and expose Retry. Retry always reacquires access; there is no authorization fallback. Negotiated playback uses HLS.js FetchLoader with omitted credentials, exact job/origin/grant validation for every child request and `redirect: 'error'`. Direct routes and the external metal reverse proxy must serve content without redirects. Native-HLS-only browsers cannot enforce redirect rejection and therefore do not use native fallback in this mode. Metal must remain allowed by the proxied response CSP's connect/media directives.

Normal website grants, existing browser delivery, uploads and shared files keep their existing behavior. Old servers lacking the capability retain Strife's existing proxy path.

Validation: `node --test test/strife-embed.test.js`, `npm run test:obs`, `npm run test:embed`, and `npm run test:obs:browser`. Strife's `npm run test:sharing` exercises the complete embedded UI and a real native WHIP publisher using generated media. Full protocol/build notes are maintained in Strife's `docs/helltube-embed.md`.
